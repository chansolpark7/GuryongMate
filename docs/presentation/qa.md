# qa — 예상 질문과 답 (초안)

> 답은 짧게(2~4문장) 말하고, 더 물으면 "근거" 칸의 내용을 꺼낸다. 숫자는 [facts.md](facts.md) 의 값만, 측정 날짜와 함께.
> **모르는 것·안 한 것은 그렇게 말한다** (예: E-UM 등급 기준, 공공누리 유형 확인, 실제 사용자 검증).

## 1. 개인정보·위치

**Q. 위치를 계속 추적하나요? 어디에 저장되나요?**
여행을 시작한 날, 앱 화면이 켜져 있는 동안에만 30m 또는 30~60초마다 보냅니다. 서버는 **마지막 위치와 이벤트만** 저장하고 전체 이동 기록은 남기지 않습니다. 도착·출발 판정에도 "반경에 처음 들어온 시각" 같은 몇 개 값만 씁니다. 백그라운드 위치·OS 지오펜스는 이번 범위가 아닙니다.
- 근거: trip/README.md §2.1·§2.2·§7, app/README.md §3.3

**Q. AI 가 저를 기억한다는데, 무엇을 기억하나요?**
사용자가 **직접 말했거나 확인한 것만** 저장합니다 (관심사, 해설 길이, 동행자 제약 등). 나이·건강 같은 민감한 추측은 저장하지 않게 했고, 항목마다 근거(어느 대화)와 시각이 남습니다. 앱의 "나에 대해"(화면 31)에서 보고 지울 수 있습니다. 탈퇴하면 일정·대화가 삭제됩니다.
- 근거: docent/README.md §1.2·§5, agent/README.md §5 "메모리", account/README.md §4
- ⚠ 주의 (2026-10-10 코드 확인): 탈퇴 연쇄 삭제는 지금 **planner·agent 만** 부른다 (`backend/app/account/router.py` `DataCleaner.SERVICES`). docent 는 `DELETE /docent/me` 가 있지만 연결되지 않았고, trip(마지막 위치·이벤트)에는 탈퇴용 API 가 없다. 고치기 전이면 "메모리도 탈퇴 시 삭제된다"고 말하지 않는다.

**Q. 로그인·인증은?**
Google 또는 아이디/비밀번호 로그인, JWT access(1시간)·refresh(30일, 재사용 감지 rotation)입니다. 다른 사용자의 계획·세션은 존재하지 않는 것처럼 404 로 답합니다. 토큰 없이 사용자 id 헤더로 부르는 것은 개발 모드에서만 됩니다.
- 근거: README.md account, planner/README.md §1.1, agent/README.md §1, app/flows.md F11

## 2. LLM 비용·속도

**Q. LLM 비용이 얼마나 드나요?**
운영 모델은 Claude Haiku 5.5 이고, 2026-10-09 실측(시나리오 4개 × 2회, 검토 루프 포함)에서 **턴당 약 $0.003** 였습니다. 입력의 약 86% 를 프롬프트 캐시에서 읽습니다. 같은 조건의 Sonnet 5.5 는 약 $0.050 이었는데 검토 기준 품질(남은 문제 0/0)이 같아 Haiku 를 골랐습니다. 장소 가이드 노트는 장소당 약 $0.002~0.004 입니다.
- 근거: agent/README.md §7·§7.1 "모델 비교", docent/README.md §3.3

**Q. 응답이 느리지 않나요?**
계획을 짜는 턴은 평균 약 16초입니다 (Haiku 15.9초, 2026-10-09). 그동안 "장소 찾기 → 일정 검토" 같은 **진행 단계가 실시간으로** 보여 기다림이 보입니다. 현장 해설은 여행 전에 만들어 둔 노트를 LLM 없이 바로 꺼내고, 위험 구역 접근 경고도 LLM 없이 즉시 뜹니다. LLM 은 개입 단계 3(선제 제안)에서만 씁니다.
- 근거: agent/README.md §3.1·§7.1, docent/README.md §4, trip/README.md §3.1

**Q. 이벤트마다 LLM 을 부르면 비용이 폭발하지 않나요?**
모든 변화에 LLM 을 쓰지 않습니다. 진행 상태·가벼운 지연은 화면만, 출발·위험 구역 접근은 고정 문구, 도착은 카드입니다. 선제 턴은 새 규칙 위반이나 남은 일정의 안전 단계 상승 때만, 한 번에 하나, 10분 쿨다운(안전 제외), 같은 원인은 다시 보내지 않습니다.
- 근거: trip/README.md §3.1·§4.1

## 3. 환각·잘못된 제안 방지

**Q. LLM 이 엉뚱하게 일정을 바꾸면요?**
LLM 은 **일정을 직접 바꾸지 못합니다.** 변경은 초안에 쌓였다가 제안 카드가 되고, 사용자가 승인해야 플래너에 반영됩니다. 거절하면 그대로입니다. 그사이 일정이 바뀌었으면 승인 때 확인창(base_changed)이 뜨고, 이미 다녀온 곳을 바꾸는 제안은 막고 다시 제안합니다. 여행 중에는 다녀온 항목 수정·지난 시각 고정을 도구 단계에서 거부합니다.
- 근거: planner/README.md §5, agent/README.md §4·§11.3

**Q. 운영시간·이동시간을 LLM 이 틀리면요?**
검증은 LLM 이 아니라 **결정론적 알고리즘**입니다 (운영시간·휴무·종료 시각·고정 시각·긴 도보·사용자 규칙). 이동시간은 직접 띄운 길찾기 엔진이 계산합니다. LLM 이 답을 끝내려 하면 하네스가 같은 규칙으로 검토해 남은 문제를 되돌려 보내고(최대 2번), 되돌려진 답은 사용자에게 보내지 않습니다. gpt-5.4-mini 비교에서 검토 루프로 남은 should 문제가 0.8 → 0 이 됐습니다 (2026-10-04).
- 근거: planner/README.md §2.4, agent/README.md §5 "검토 루프", §7 "모델·구조 비교"

**Q. 해설에 없는 사실을 지어내지 않나요?**
해설은 관광공사 소개문·오디오 가이드(근거 조각 430개)와 검색 자료에서만 씁니다. 노트는 **실제로 본 자료만** 출처로 남기고, 지어낸 URL 은 버리며, 출처가 하나도 없으면 노트를 실패로 둡니다. 출처 등급(공식·언론·커뮤니티)은 LLM 이 아니라 서버가 도메인으로 정하고, 커뮤니티 정보는 "방문 후기로는"처럼 구분합니다. 2026-10-09 표본 대조에서 연도·인물이 근거 자료와 맞았습니다.
- 근거: docent/README.md §2.2·§3.1·§3.3·§5.2, agent/README.md §12

**Q. 웹 페이지 안의 문장이 AI 에게 지시를 내리면요?**
가져온 내용은 자료이지 지시가 아니라고 프롬프트에 명시합니다. 페이지 읽기는 사설·내부 주소를 막고(리다이렉트마다 다시 검사), 크기·시간 제한이 있습니다.
- 근거: docent/README.md §2.3, agent/README.md §11.3.1

## 4. DT 데이터 신뢰도

**Q. E-UM 수위 등급 2·3 을 위험으로 본 근거는?**
**가정입니다.** E-UM 이 등급 체계·값 단위·임계값을 공개하지 않았고, 평상시 실측은 전부 등급 1 이라 2·3 을 관측하지 못했습니다. 그래서 "1 평상시, 2 주의, 3 이상 위험"으로 해석하고, 이 가정을 응답의 `assumptions` 에 그대로 적어 보냅니다. 포털 문의 또는 악천후 관측으로 확정하는 것이 다음 할 일입니다.
- 근거: safety/README.md §3 "판단 기준"·§8, DT_API.md §2

**Q. DT 가 예측해 주는 건가요?**
아닙니다. 공개 API 에는 침수 예측·방파제 이동 예측·경보 API 가 없고 **실측값**(수위 센서 10대, 방파제 AI CCTV 이상행동 시간별 집계, 자외선)만 있습니다. 그래서 "DT 실측 + 기상청 예보·특보를 우리가 해석해 일정 위험도로 바꾼다"로 설계했습니다. 미래 시각의 날씨 위험은 예보로, 실측 센서·CCTV 는 방문 3시간 안에만 씁니다.
- 근거: DT_API.md §4 "기획서와의 차이", safety/README.md §2

**Q. 데이터가 늦거나 끊기면 '안전'으로 나오지 않나요?**
아닙니다. 판단에 필요한 데이터를 못 받으면 `safe` 가 아니라 **"판단 불가"(null)** 입니다. 다른 근거로 위험이 확인되면 그 단계를 주고 "빠진 데이터 때문에 실제로는 더 높을 수 있음"을 붙입니다. 경고도 데이터 장애를 해제로 오인하지 않게 지난 단계를 유지합니다. 수위 응답에 측정 시각이 없어 수집 시각을 기록하고, CCTV 집계는 약 하루 늦어 최근 3시간 집계만 씁니다.
- 근거: safety/README.md §3·§4, planner/README.md §7.3, DT_API.md §2·§3

**Q. 방파제 CCTV 접근 경고는 평소에도 많던데요?**
맞습니다. 평상시에도 접근·침입이 두 자릿수로 찍혀서, 접근·침입 20건/시는 "참고"로만 두고 단계를 올리는 것은 **실족 감지 1건 이상**(주의)입니다. 시간대별 평소값(baseline) 대비 급증으로 판단하는 것은 과거 데이터를 쌓아야 해서 다음 할 일입니다.
- 근거: DT_API.md §3, safety/README.md §3·§8

## 5. 먼 날짜는 판단하지 않는다

**Q. 다음 달 여행인데 날씨 위험을 알려 주나요?**
아니요, 일부러 하지 않습니다. 단기예보가 있는 약 3일 안까지만 판단하고, 그 뒤는 `risk=null` 과 함께 "안전을 이유로 일정을 바꾸지 마라", 그리고 다시 확인할 날짜(방문 3일 전)를 줍니다. 지금 폭풍이어도 몇 달 뒤 일정에는 영향을 주지 않는다는 테스트가 있습니다. 먼 날짜에는 천문 계산이라 정확한 만조·간조 시각과 계절 경향만 참고로 줍니다.
- 근거: safety/README.md §2 (`test_far_future_is_not_assessed_and_says_do_not_change`), §1 `/safety/outlook`

**Q. 지금 특보가 내려져 있으면 내일 일정도 위험한가요?**
특보는 '지금' 상태라 방문 6시간 안에만 그대로 쓰고, 6~24시간은 참고, 그 뒤는 쓰지 않습니다. 내일 오후 예보가 잠잠하면 내일 오후 방파제는 안전입니다.
- 근거: safety/README.md §2 "발효 중 특보"

## 6. 실제 운영 시 확장

**Q. 사용자가 많아지면요?**
기능별로 컨테이너가 나뉘어 있고 서비스끼리는 게이트웨이 경유 HTTP 로만 통신해서, 부하가 큰 서비스만 따로 늘리거나 바꿀 수 있는 구조입니다. 다만 지금은 **단일 인스턴스 기준**입니다: safety 캐시, 가이드 준비 작업 기록, 선제 턴 재시도 대기 시각이 프로세스 메모리에 있어, 여러 대로 늘리려면 공유 저장소로 옮겨야 합니다. 외부 호출은 캐시로 줄여 E-UM 시간당 약 42회 수준이고 이는 사용자 수와 무관합니다 (safety 는 사용자 일정을 모름).
- 근거: COLLABORATION.md §1·§2, safety/README.md §1 `/safety/situation`·§4, agent/README.md §12, trip/README.md §4.1

**Q. 아직 안 된 것은?**
대중교통 길찾기(도보·차량만), 3~10일 중기예보·재난문자 연동, 동행자 특성(폭염·한파) 반영, 앱 백그라운드 알림·위치, 음성(TTS — 노트를 그대로 읽으면 돼 붙이기 쉬움), 혼잡도 데이터(없음).
- 근거: routing/README.md §8, safety/README.md §7·§8, app/gaps.md b12·b14, docent/README.md §4

**Q. 다른 지역에도 쓸 수 있나요?**
위험 판단은 safety 한 곳에 모여 있어서, 다른 지역은 그 지역 데이터 소스·감시 구역을 safety 에 더하면 planner(일정 점검)·trip(이벤트)·agent(제안)는 바꾸지 않아도 됩니다. 길찾기는 OSM 영역만 바꿔 다시 빌드합니다. 장소 데이터는 관광공사 API 로 지역 단위 수집입니다.
- 근거: architecture.md §2, planner/README.md §7, routing/README.md §4, places 수집 (README.md)

## 7. 포항 DT 서비스와의 연계

**Q. E-UM 포항과 실제로 연결돼 있나요?**
네. 침수·방파제 API 12개를 모두 활용신청하고 실제 응답을 확인했습니다 (2026-10-04, 원본 응답을 `docs/dt/raw/live/` 에 저장). 실시간으로 쓰는 것은 수위 센서(10대), 방파제 AI CCTV 이상행동 집계, 자외선입니다. 장비 목록 API 로 센서·CCTV 좌표를 받아 감시 구역(방파제 선 + 60m, 센서 반경 200m)을 정의했습니다.
- 근거: DT_API.md §0·§1·§3

**Q. 포항시 DT 서비스에 어떻게 붙을 수 있나요?**
우리 쪽 입력은 E-UM 공개 API 그대로라 키만 바꾸면 됩니다. 반대로 우리가 만든 "장소·시각·경로 → 위험 단계 + 근거" API(`/safety/assess`, `/safety/avoid`)는 다른 서비스가 그대로 쓸 수 있는 형태입니다. E-UM 이 예측·경보 API 나 등급 기준을 공개하면 safety 안에서 해석 기준만 바꾸면 됩니다. 방파제 스피커는 공개 API 가 장비 정보뿐이라 쓰지 않았습니다.
- 근거: safety/README.md §1, DT_API.md §3·§4

## 8. 유지보수

**Q. 유지보수는 어떻게 하나요?**
서비스마다 담당·코드·테이블 접두사·문서가 나뉘어 있고, 다른 서비스의 코드나 테이블을 직접 건드리지 않는 규칙입니다. 테스트 함수 506개(2026-10-10 집계)가 서비스별로 있고, 데모 장면은 재생 파일로 같은 파일을 CLI 와 pytest 가 함께 씁니다. 앱이 받는 응답이 바뀌면 각본 LLM 스택에서 앱 fixture 를 다시 녹화하는 규칙도 있습니다.
- 근거: COLLABORATION.md §1·§2, trip/README.md §8, app/fixtures.md

**Q. LLM 모델을 바꾸려면?**
서버 환경변수 하나(`AGENT_PROVIDER`, 모델 이름)입니다. 앱은 어떤 LLM 인지 모릅니다. Claude·OpenAI·로컬 Ollama·각본 LLM 이 같은 인터페이스이고, 같은 시나리오로 비교하는 평가 스크립트(`eval_agent.py`)가 있습니다.
- 근거: agent/README.md 머리말·§7

## 9. 저작권·공공누리

**Q. 관광공사 자료를 써도 되나요?**
관광공사 TourAPI 를 공공데이터포털에서 활용신청해 받습니다. 해설은 원문을 길게 옮기지 않고 **요약해서 새로 쓰며**, 노트마다 출처(관광공사 소개·오디오 가이드, 주소)를 남깁니다. 다만 자료별 **공공누리 유형과 표시 조건 확인은 아직 미결 항목**이라, 서비스 공개 전에 확인해 출처 표시를 맞춥니다.
- 근거: docent/README.md §3.1·§8.3, PROJECT.md §10 ("해설 콘텐츠 저작권(공공누리) 확인" 미완료), places/README.md (데이터 출처)

**Q. 지도·길찾기 데이터는?**
길찾기는 OpenStreetMap 포항 데이터로 직접 띄운 엔진이고, 지도 화면·장소 검색은 Kakao 를 씁니다. (OSM 출처 표시·지도 제공자 약관 검토는 PROJECT.md §10 의 미결 항목 "지도 UI 제공자 확정 및 혼합 사용 약관 검토"에 있다 — 확인 전이면 그렇게 답한다.)
- 근거: routing/README.md 머리말, PROJECT.md §5 M2·§10

## 10. 오프라인·장애 시

**Q. 서버나 외부 API 가 죽으면요?**
- 길찾기 엔진이 없으면 직선거리 × 1.3 으로 근사하고 "약 9분"처럼 표시합니다 (실패하지 않음).
- 안전 데이터 소스가 실패하면 그 판단은 "판단 불가"이고 어떤 소스가 실패했는지 함께 줍니다. 외부 장애 때 요청마다 다시 부르지 않게 실패도 30초 기억합니다.
- trip 은 planner 장애면 위치를 저장하지 않고 503 → 앱이 다시 보내면 다시 판정, 선제 턴 전송은 간격을 늘려 3번까지 재시도 후 `failed` 로 남깁니다.
- Agent 는 trip·docent 가 응답하지 않으면 계획 모드·메모리 없이 계속하고, LLM 오류는 원문 대신 고정 문구로 알립니다. 어느 경우든 **일정은 그대로**입니다.
- 근거: routing/README.md §1, safety/README.md §3·§4, trip/README.md §2.1·§4.1, agent/README.md §3·§11.1

**Q. 휴대폰이 오프라인이면요?**
앱은 "오프라인 · 연결되면 다시 불러올게요" 띠를 보여주고, 동행 중이면 위치를 모아 두었다가 연결되면 한 번에(`points`) 보냅니다. 서버는 받은 시각 순으로 판정합니다.
- 근거: app/README.md §6.3, trip/README.md §2.1·§2.2

**Q. 발표 중에 LLM 이 안 되면요?**
각본 LLM(`AGENT_PROVIDER=scripted`)으로 바꿉니다. 실제 LLM 을 부르지 않고 각본대로 답하지만, 도구·제안 카드·검토 관문·이벤트 흐름은 진짜로 돕니다. 운영에는 쓰지 않습니다.
- 근거: agent/README.md §7.2, demo_script.md §0.4

## 11. 그 밖에

**Q. Google Maps·Wanderlog 같은 서비스와 뭐가 다른가요?**
"AI + 플래너 + 지도 + 추천"은 이미 있습니다. 우리는 ① 구룡포 DT 안전 데이터 해석 ② 여행 중 **현재 상태**(위치·진행·남은 일정) 유지 ③ 영향이 있을 때만 먼저 개입 ④ 근거 있는 맞춤 해설 ⑤ 모든 변경은 승인 — 이 조합이 차별점입니다.
- 근거: PROJECT.md §1 "주의할 포지셔닝"

**Q. 혼잡도·실시간 교통은요?**
혼잡도 데이터는 없어서 화면에서도 "데이터 없음"으로 둡니다. 차량 시간은 도로 종류별 기본 속도이고 구룡포 규모에서는 충분하다고 봤습니다.
- 근거: app/gaps.md b14, routing/README.md §8

**Q. 실제 사용자로 검증했나요?**
아직 실제 사용자 테스트 기록은 없습니다. 검증은 데모 시나리오 재생(장면 ②③④ 기대 이벤트 모두 통과, 2026-10-09)과 서비스별 테스트, 실제 LLM 평가 스크립트로 했습니다.
- 근거: trip/README.md §8, agent/README.md §7.1
