# demo — 발표 데모 운영 (2026-10-13 본선)

발표 데모를 **진행 스크립트 하나**로 장면 단위로 끌고 가고, 문제가 생기면 정해 둔 방법으로 대처한다.

| | |
|---|---|
| 서버 | GCP VM 에서 `docker compose` 전체 스택 (gateway 하나로 접속) |
| 앱 | 노트북의 Android 에뮬레이터. **데모 위치 모드**(설정 33)로 서버에 들어온 위치를 지도에 그린다 (발표장은 구룡포가 아니다) |
| 진행 | `scripts/demo/run_demo.py` — 노트북에서 실행, 서버에 위치·시각·가상 상황·대화를 보내고 단계마다 앱에 보여야 할 것을 안내 |
| 장면 | PROJECT.md §3 의 4장면을 **한 계획으로 이어서** (① 계획 → ② 도착·해설 → ③ 지연 → ④ DT 안전) |
| 데모 데이터 | docs/app/README.md §6.1 — 엄마랑 구룡포 10/10 12:30~18:00, 가옥거리 → 구룡포항 → 과메기문화관 → 북방파제 → 카페파도 |
| 백업 | 같은 진행 스크립트 + 에뮬레이터 화면 녹화 영상 (§5) |

## 1. 구성

```
노트북 ─┬─ Android 에뮬레이터 (앱, 데모 사용자로 로그인, 데모 위치 모드)  ──┐
        └─ run_demo.py (같은 사용자로 로그인)                              ──┼──► GCP VM gateway :8000
                                                                             │     agent (Claude Haiku 5.5 | 각본)
                                                                             │     safety (실제 E-UM·기상청 ↔ 가상 상황)
                                                                             │     trip · planner · places · routing · docent · account
```

- 앱과 스크립트는 **같은 사용자**(`seoyun-demo`)로 로그인한다. 스크립트가 만든 계획·여행 상태·이벤트·대화를 앱이 그대로 본다.
- 시각은 safety 의 가상 시각 하나를 모든 서비스가 따른다 (docs/trip/README.md §5). 스크립트가 장면마다 10/9 10:00(여행 전날) → 10/10 12:25 … 로 옮긴다.
- 장면 ④ 의 '실제 DT 데이터 → 가상 악천후' 전환은 safety 의 `SAFETY_SIM_ENABLED=true` 가 필요하다 (docs/safety/README.md §1 `/safety/sim`).

### 서버 설정 (VM 의 `backend/.env`, 루트 `.env`)

| 변수 | 발표 값 | 왜 |
|---|---|---|
| `AGENT_PROVIDER` | `claude` | 실제 LLM (Haiku 5.5). 문제 시 `scripted` (§4.1) |
| `AGENT_CLAUDE_API_KEY` | (키) | 크레딧 확인 (§2) |
| `SAFETY_SOURCE` | `live` | 실제 E-UM 디지털트윈·기상청 데이터로 시작 |
| `SAFETY_SIM_ENABLED` | `true` | 실행 중 실제 ↔ 가상 전환, 가상 시각 |
| `DT_SERVICE_KEY`, `DATA_GO_KR_SERVICE_KEY` | (키) | 실제 데이터. 없으면 장면 ④ 실데이터 단계만 '판단 보류' 로 보인다 |
| `AUTH_REQUIRED` | `true` | 공개 VM 이므로 로그인 필수. 대신 즉시 안전 점검(`POST /planner/safety/scan`)을 못 쓴다 → 아래 |
| `PLANNER_SAFETY_WATCH_SEC` (루트 `.env`) | `10` | 기본 60초. 가상 악천후로 바꾼 뒤 planner 가 상황 변화를 알아채는 주기 — 장면 ④ 의 선제 턴이 이만큼 늦게 시작한다 |
| `TRIP_TICK_SEC` (루트 `.env`) | 기본 30 | 스크립트가 필요한 때 틱을 직접 부른다 |

## 2. 발표 당일 체크리스트

### T-60분 (서버)
- [ ] `docker compose ps` — 모든 서비스 `healthy`/`running` (places-init 은 `exited 0`)
- [ ] 서비스 점검 (진행 스크립트 시작 화면도 같은 것을 보여준다, T-15):
  ```bash
  curl http://<VM>:8000/agent/info          # {"provider": "claude:claude-haiku-5-5"}
  curl http://<VM>:8000/safety/sim          # "mode": "live", "switchable": true
  curl http://<VM>:8000/safety/status       # data_status 의 sensors·breakwater·forecast·warnings 가 모두 ok
  curl http://<VM>:8000/routing/status      # engine.ok = true
  ```
- [ ] **키·크레딧**: Anthropic Console 에서 남은 크레딧 확인 (처음부터 끝까지 1회 약 $0.04, §6 — 리허설 여러 번 + 본 발표 + Q&A 로 $1 이상 남아 있으면 충분). 공공데이터포털·E-UM 키는 하루 호출 한도(개발계정 10,000건) 안인지.
- [ ] **실제 데이터 확인**: `/safety/status` 의 `overall_risk`. 실제 날씨가 이미 주의·위험이면 장면 ④ 실데이터 단계에서 바로 경고가 나갈 수 있다 → 그 단계를 건너뛸지(§3 `s`) 미리 정한다.
- [ ] 디스크·메모리: `df -h`, `free -m` (Valhalla·임베딩이 메모리를 많이 쓴다).

### T-30분 (노트북)
- [ ] 전원 연결, 절전·화면 꺼짐·자동 업데이트 끔. 알림 끔(방해 금지).
- [ ] 네트워크: 발표장 Wi-Fi 로 VM 접속 확인. **휴대폰 핫스팟을 대기**해 둔다 (지도 타일·서버 모두 인터넷이 필요).
- [ ] 에뮬레이터: AVD 부팅 (느리면 Cold Boot), 앱 설치본이 `--dart-define=DEMO=true` 빌드인지 (설정에 '데모 · 개발' 그룹이 보여야 함).
- [ ] 앱 설정(33): 서버 주소 `http://<VM>:8000` → [연결 확인] "agent: claude… · safety: …".
  데모 사용자 `seoyun-demo` 로 로그인. **데모 위치 모드 켬**.
- [ ] **지도 타일**: 앱 지도는 flutter_map + 공용 OSM 타일이다 (app/README.md). 구룡포 일대를 데모에서 쓸 확대 수준으로 한 번 훑어 캐시해 둔다.
  타일이 안 뜨면 네트워크(핫스팟) 문제다.
- [ ] Python 3.11+ 와 `httpx` (`pip install httpx`). 저장소는 발표 브랜치.
- [ ] 백업 영상 파일을 노트북에 두고 플레이어로 열어 둔다 (§5).

### T-15분 (진행 스크립트)
```bash
python scripts/demo/run_demo.py --url http://<VM>:8000
```
- 시작 화면에서 **LLM**(`claude:claude-haiku-5-5` 초록 / `scripted` 노랑), **안전**(실제 ↔ 가상 전환 가능), **길찾기**(Valhalla 정상)를 확인한다.
- 첫 단계 `prep`(준비)만 실행해 둔다: 이 사용자의 계획·여행 상태·메모리·노트를 지우고 빈 계획 '엄마랑 구룡포' 를 만든다.
  앱 홈을 새로고침해 계획 하나가 보이는지 확인. (스크립트는 그대로 두고 다음 단계에서 멈춰 있게 한다)
- 리허설을 했다면 반드시 `prep` 을 다시 한다 (메모리 '해설은 핵심만 짧게' 가 남아 있으면 장면 ② 가 달라진다).

## 3. 진행 순서

```bash
python scripts/demo/run_demo.py --url http://<VM>:8000                     # 기본: 장면 ① 을 대화로, 대화는 스크립트가 보냄
python scripts/demo/run_demo.py --url http://<VM>:8000 --plan prebuilt     # 장면 ① 을 미리 만든 계획으로 (대화 단계 없음)
python scripts/demo/run_demo.py --url http://<VM>:8000 --chat app          # 대화·승인을 발표자가 앱에서 (스크립트는 결과를 기다렸다 보여줌)
```

| 키 | 단계 전 | 단계 후 |
|---|---|---|
| Enter | 실행 | 다음 단계로 |
| `s` | 건너뛰기 | |
| `b` | 이전 단계로 | |
| `l` | 단계 목록 | |
| `r` | | 이 단계 다시 |
| `q` | 끝내기 (결과 표 출력) | |

| 옵션 | 기본 | |
|---|---|---|
| `--speed` | 20 | 이동할 때 가상 시각 배속 (도보 10분 = 30초). 0 이면 기다리지 않음 |
| `--stay-speed` | 120 | 한 자리에 머무는 동안 배속 (장면 ③ 의 90분 머묾 = 45초) |
| `--plan` | `chat` | `prebuilt`: 미리 만든 계획 |
| `--chat` | `script` | `app`: 발표자가 앱에서 입력·승인 |
| `--auto`, `--pause` | | 멈추지 않고 끝까지 (리허설·백업 영상), 단계 사이 대기 초 |
| `--from <id>` | | 그 단계부터 (계획·위치·시각은 진행 상태 파일 `~/.guryongmate/demo_state.json`) |
| `--fast-to <id>` | | 준비부터 그 단계 앞까지 기다리지 않고 진행한 뒤 거기서부터 한 단계씩 (§4.1) |
| `--log <파일>` | | 단계별 소요 시간·기대 결과 JSON |

- `--chat script` 면 대화는 스크립트가 보내고 터미널에 실시간으로 보인다. 앱은 대화 화면을 다시 불러야 그 대화를 그린다 (앱의 세션 갱신 방식에 따름).
  앱 화면에서 입력이 보이는 것이 중요하면 `--chat app` 으로 발표자가 앱에 직접 입력한다. 각본 LLM 일 때는 아래 문장을 **그대로** 입력해야 한다.
- 각 단계 끝에 `앱 화면 ▶` 줄이 그 단계 뒤 앱에 보여야 할 것이다. 기대 이벤트·카드는 `기대 …: 통과/실패`, `확인 …: 통과/실패` 로 바로 보인다.

## 4. 문제별 대처

### 4.1 LLM 오류 (대화가 `llm_unavailable`·`llm_quota`, 선제 턴 `failed`, 응답이 1분 넘게 없음)

**각본 LLM 으로 바꾼다** (`AGENT_PROVIDER=scripted`). 실제 LLM 을 부르지 않고 데모 문장에 정해진 답을 한다 (docs/agent/README.md §7.2).

```bash
# VM 에서 (저장소 루트)
sed -i 's/^AGENT_PROVIDER=.*/AGENT_PROVIDER=scripted/' backend/.env
docker compose up -d agent          # agent 컨테이너만 다시 만든다 (env_file 변경 반영)
curl -s localhost:8000/agent/info   # {"provider": "scripted:scripts"}
```
- 걸리는 시간: **약 6~8초** (§6 실측). 그 뒤 실패한 단계를 다시 하거나 빨리 감기(각본 LLM 이면 장면 ④ 앞까지 약 40초).
- 되돌리기: 같은 명령으로 `AGENT_PROVIDER=claude`.
- 바꾼 뒤 이어서 하기:
  - **대화 단계**(`s1_chat`·`s2_ask`·`s2_shorter`·`s3_keep`·`s1_cafe`)에서 실패: 그 단계에서 `r`(다시).
  - **선제 턴**(`s3_delay`·`s4_storm`)이 실패: 같은 원인으로는 다시 알리지 않는다 (중복 억제, docs/trip/README.md §4.1). 진행 스크립트를 끝내고(`q`)
    ```bash
    python scripts/demo/run_demo.py --url http://<VM>:8000 --fast-to s3_delay    # 또는 s4_storm
    ```
    로 준비부터 그 단계 앞까지 빨리 감는다 (기다리지 않음, 각본 LLM 이면 `s4_storm` 앞까지 약 36초 — §6). 앱은 새 계획을 보도록 홈에서 새로고침.
- 각본 LLM 은 정해진 문장만 안다: «엄마랑 구룡포 일정 짜줘», «갈 만한 카페 추천해줘», «언제 지어진 집들이에요?», «왜 이름이 구룡포야?», «다음부터는 더 짧게 해줘요», «과메기문화관은 유지해줘», 선제 턴(지연·안전).
  그 밖의 말에는 고정 안내("지금은 데모용 각본 모드라…")가 나온다. 즉석 질문(Q&A)은 받지 않는다.
- 크레딧 부족(`llm_quota`)은 키를 바꿔도 되지만, 발표 중에는 각본으로 바꾸는 쪽이 빠르다.

### 4.2 safety 외부 API 장애 (실제 데이터)
- 증상: `s4_live` 단계 출력에 `받지 못한 데이터: …` (노랑), 앱 안전 화면에 '판단 보류'(risk 없음).
- 대처: **그 단계를 건너뛴다** (`s`). `s4_storm` 의 가상 상황은 외부 API 를 쓰지 않으므로 그대로 된다.
  말로 "실제 연동은 되어 있고 지금 외부 API 가 응답하지 않는다" 정도만.
- 장애가 미리 보이면(T-60 점검) 서버를 그대로 두고 `s4_live` 를 빼고 진행한다. safety 를 다시 띄울 필요는 없다 (각 소스는 실패해도 30초 뒤 다시 시도한다).
- 실제 날씨가 이미 나쁘면(실데이터에 주의·위험) `s4_live` 로 바꾸는 순간 planner 가 실제 위험으로 경고를 낼 수 있다. 이것도 이야기가 되지만, 흐름을 지키려면 `s4_live` 를 건너뛴다.

### 4.3 서버 다운 (게이트웨이 응답 없음·5xx 연속)
- 1분 안에 판단한다: VM 에서 `docker compose ps` → 멈춘 서비스만 `docker compose restart <서비스>` (수십 초).
  전체를 다시 띄우면 수 분 걸린다 (임베딩·Valhalla 준비).
- 1분 안에 안 되면 **백업 영상**(§5)으로 넘어간다. 영상은 장면별로 잘라 두어 이어서 틀 수 있게 한다.
- 다시 살아나면 `--fast-to <다음 장면 첫 단계>` 로 이어서 할 수 있다 (가상 시각 맞춤 포함).

### 4.4 그 밖
| 증상 | 대처 |
|---|---|
| 기대 `실패` (예: 도착이 안 나옴) | 그 단계 `r`. 계속 실패하면 `s` 로 넘기고 말로 설명 |
| 앱 로그인 만료 | 앱에서 다시 로그인 (스크립트와 같은 아이디) |
| 앱에 위치가 안 움직임 | 데모 위치 모드가 켜져 있는지, 같은 계획을 보고 있는지 (`prep` 뒤 홈 새로고침) |
| 지도 타일 안 뜸 | 핫스팟으로 바꿈. 안 되면 영상 |
| 에뮬레이터 멈춤 | 앱만 다시 실행 → 안 되면 영상. 서버 상태는 스크립트가 들고 있으므로 다시 열면 이어진다 |
| 대화가 앱에 안 보임 (`--chat script`) | 앱에서 대화 화면을 다시 연다. 또는 `--chat app` 으로 다시 |

## 5. 백업 영상 촬영

같은 진행 스크립트로 처음부터 끝까지 진행하면서 **에뮬레이터 화면을 녹화**한다. 실제 LLM(Claude)으로 한 번, 각본 LLM 으로 한 번 찍어 둔다.

1. 서버는 발표와 같은 설정 (§1). 앱은 로그인·데모 위치 모드.
2. 녹화 도구 (둘 중 하나):
   - **OBS Studio** (권장): 에뮬레이터 창을 '윈도우 캡처', 1080p 30fps. 길이 제한이 없고 터미널을 같이 넣을 수도 있다.
   - 에뮬레이터 Extended controls(⋯) → **Record and Playback** → Start recording (webm 저장).
   - `adb shell screenrecord /sdcard/demo1.mp4` 는 한 파일 최대 3분이라 장면마다 따로 찍어야 한다.
3. 진행:
   ```bash
   python scripts/demo/run_demo.py --url http://<VM>:8000 --log video_run.json   # 한 단계씩 (앱을 조작하며 찍기 좋음)
   python scripts/demo/run_demo.py --url http://<VM>:8000 --auto --pause 8       # 자동 (단계 사이 8초)
   ```
   `prep` 을 실행해 앱 홈을 새로고침한 뒤 녹화를 시작한다. 단계마다 '앱 화면 ▶' 줄에 있는 화면(채팅 펼치기, 카드 열기, 안전 화면)을 앱에서 열어 보여준다.
4. 장면별로 자르고(①~④), 결과 표(`--log`)의 기대가 모두 통과한 녹화만 쓴다.
5. 노트북에 파일로 두고 발표 직전 플레이어로 열어 둔다 (인터넷 없이 재생).

## 7. 앱 쪽 참고 (앱 작업에 전달할 것)

- `GET /safety/sim` 은 `SAFETY_SIM_ENABLED=true` 면 실제 데이터 모드에서도 200 이다. 설정 33 의 "가상 상황/실제 데이터" 표시는 404 여부가 아니라 응답의 **`mode`**(`live`|`sim`)로 정한다.
  `switchable` 이면 "실제 데이터 ↔ 가상 상황" 전환(`PUT /safety/sim {"source": "live"|"mock"}`)을 줄 수 있다.
- `GET /safety/status` 에 `mode`·`scenario` 가 있다. 안전 화면에 "실제 데이터 (E-UM 디지털트윈)" / "가상 상황: 폭풍" 표시를 붙이면 장면 ④ 의 전환이 화면에서 보인다.
- 진행 스크립트가 보낸 대화(`--chat script`)를 앱이 보려면 대화 화면이 세션(`GET /agent/sessions/{id}`)을 다시 불러야 한다 (선제 턴 메시지와 같은 방식).
